## Overview

The `tools/` directory contains various Python-based utilities and scripts that support the OpenHarmony build system. These tools handle component management, dependency analysis, static code checking, and product configuration conversion.

## 1. Product Configuration Converter

### File: `product_config_version_convert.py`

**Purpose**: Converts product configuration files from the old format (2.0) to the new 3.0 format used by OpenHarmony.

**Usage**:
```bash
python3 product_config_version_convert.py {product_name}.json
```

**Key Functions**:
- `merge_files()`: Merges product and device configuration files
- `readjson()`: Reads and transforms config to 3.0 format
- `merge()`: Merges two dictionaries

**Integration**: Used during product migration to adapt existing products to new build system requirements.

## 2. Dependency Checker (`check_deps/`)

### File: `check_deps.py`

**Purpose**: Validates that module dependencies in BUILD.gn files correctly use `deps` (internal) vs `external_deps` (inter-part).

**Problem Solved**: Developers sometimes mistakenly put inter-part dependencies in `deps` instead of `external_deps`, violating the component architecture.

**Usage**:
```bash
# First, build with check_deps enabled
./build.sh --product-name {product} --gn-args check_deps=true --build-only-gn

# Then run the checker
python3 build/tools/check_deps/check_deps.py \
    --parts-path-file out/{product}/build_configs/parts_info/parts_path_info.json \
    --deps-path out/{product}/deps_files
```

**Output**: `wrong_used_deps.json` - Lists modules with incorrectly categorized dependencies.

**Integration**: Works with GN build output to analyze dependency declarations.

## 3. Module Dependency Analysis (`module_dependence/`)

This package provides comprehensive dependency analysis at both module and part levels.

### 3.1 Core Analysis Module

**File: `dependence_analysis.py`**
- Reads module dependency files generated by GN
- Parses external dependencies
- Merges internal and external dependency labels
- **Key Function**: `get_all_deps_data()` - Returns complete dependency graph

### 3.2 Module Dependencies

**File: `module_deps.py`**

**Purpose**: Generates module-level dependency information.

**Usage**:
```bash
python3 build/tools/module_dependence/module_deps.py \
    --deps-files-path out/{product}/deps_files
```

**Output**:
- `all_deps_data.json` - Raw dependency data with labels
- `module_deps_info.json` - Consolidated module dependencies

### 3.3 Part Dependencies

**File: `part_deps.py`**

**Purpose**: Generates part/component-level dependency information and visualizations.

**Usage**:
```bash
python3 build/tools/module_dependence/part_deps.py \
    --deps-files-path out/{product}/deps_files \
    --graph  # Optional: generates HTML dependency graph
```

**Output**:
- `part_deps_info.json` - Part-level dependencies
- `part-deps-graph.html` - Interactive dependency visualization (requires pyecharts)

### 3.4 Module Dependency Tree

**File: `module_deps_tree.py`**

**Purpose**: Generates tree visualization for a specific module's dependencies.

**Usage**:
```bash
python3 build/tools/module_dependence/module_deps_tree.py \
    --module-name {part_name}:{module_name} \
    --module-deps-file out/{product}/module_deps_info/module_deps_info.json
```

**Output**: `{part_name}__{module_name}.html` - Interactive tree diagram

### 3.5 Utilities

**File: `file_utils.py`**
- JSON file reading/writing utilities
- Handles encoding and error cases

**Integration**: All tools require GN build output with `check_deps=true` flag.

## 4. Component Tools (`component_tools/`)

### 4.1 Kconfig Generator

**File: `generate_kconfig.py`**

**Purpose**: Generates Kconfig files from product configuration for menu-driven component selection.

**Usage**:
```bash
python3 generate_kconfig.py \
    --base_product=productdefine/common/base/base_product.json \
    --outdir=./
```

**Output**: `kconfig` file for use with kconfig-frontends

### 4.2 Kconfig Parser

**File: `parse_kconf.py`**

**Purpose**: Parses `.config` files (generated from Kconfig) back to JSON product configuration.

**Usage**:
```bash
python3 parse_kconf.py \
    --deps=out/{product}/part_deps_info/part_deps_info.json \
    --base_product=productdefine/common/base/base_product.json \
    --config=./.config \
    --out=./product.json
```

**Key Feature**: Automatically adds transitive dependencies to the configuration.

### 4.3 Component Node Model

**File: `component_node.py`**

**Purpose**: Data models for component and module representation.

**Classes**:
- `Module`: Represents a single build target with deps/external_deps
- `Node`: Represents a component (part) containing multiple modules

**Usage**: Used by `components_dependence_analysis.py` for parsing BUILD.gn files.

### 4.4 Component Dependency Analysis

**File: `components_dependence_analysis.py`**

**Purpose**: Analyzes BUILD.gn files and generates component dependency graphs using Graphviz.

**Usage**:
```bash
python3 components_dependence_analysis.py \
    --root-path {ohos_root} \
    --output {output_path}
```

### 4.5 Full Components Generator

**File: `full_components_generator.py`**

**Purpose**: Generates the `base_product.json` containing all available components in the system.

**Usage**:
```bash
python3 full_components_generator.py \
    --subsys=build/subsystem_config.json \
    --out=productdefine/common/base/base_product.json
```

**Integration**: Scans `ohos.build` and `bundle.json` files across all subsystems.

## 5. Component Static Check Tool (`component_tools/static_check/`)

CSCT is a comprehensive static analysis tool that validates component build configurations against OpenHarmony coding standards.

### 5.1 Main Entry Point

**File: `csct.py`**

**Purpose**: Local static checking of BUILD.gn and bundle.json files.

**Usage**:
```bash
# Check entire codebase
python3 build/tools/component_tools/static_check/csct.py

# Check specific path
python3 build/tools/component_tools/static_check/csct.py -p base/global

# Check PR diffs
python3 build/tools/component_tools/static_check/csct.py -cd diff_files.txt
```

**Output**: `out/output_errors.xlsx` - Consolidated error report

**Checked Rules**:
- Rule 2.1: Component description fields must be accurate
- Rule 3.1: No absolute/relative paths to other components in BUILD.gn
- Rule 3.2: All targets must specify `part_name` and `subsystem_name`
- Rule 4.1: No product-specific variables in component scripts

### 5.2 Online/CI Version

**Files**: `csct_online.py`, `csct_online_entry.py`, `csct_online_prehandle.py`

**Purpose**: CI/CD integration for checking pull requests.

**Flow**:
1. `csct_online_entry.py` - Entry point for CI system
2. `csct_online_prehandle.py` - Fetches and parses PR diffs from Gitee
3. `csct_online.py` - Runs checks only on modified files

**Usage**:
```bash
python3 csct_online.py "https://gitee.com/repo/pulls/123"
```

### 5.3 GN Check Module

**Files**: `gn_check/check_gn.py`, `gn_check/check_gn_online.py`, `gn_check/gn_common_tools.py`

**Purpose**: Validates BUILD.gn files against coding standards.

**Checks**:
- Absolute path references (Rule 3.1)
- Missing `subsystem_name`/`part_name` (Rule 3.2)
- Product-specific code (Rule 4.1)

**Key Class**: `CheckGn` - Main checking engine with whitelist support

### 5.4 Bundle Check Module

**Files**: 
- `bundle_check/bundle_json_check.py` - Full bundle.json validation
- `bundle_check/bundle_check_online.py` - PR diff checking
- `bundle_check/bundle_check_common.py` - Utility functions
- `bundle_check/get_subsystem_with_component.py` - Subsystem mapping
- `bundle_check/warning_info.py` - Error message constants

**Purpose**: Validates bundle.json component descriptor files.

**Validations**:
- Name format: `@organization/component_name`
- Version matches OpenHarmony version
- destPath is relative and valid
- subsystem is lowercase
- syscap follows SystemCapability naming
- rom/ram values with proper units

**Usage**:
```bash
# Check all bundle.json files
python3 bundle_json_check.py -P /path/to/project

# Check specific files
python3 bundle_json_check.py -p path/to/bundle.json
```

### 5.5 Whitelist Configuration

**File**: `config/csct_whitelist.conf`

Contains directories excluded from checking:
- `out` - Build output
- `vendor` - Vendor-specific code
- `device` - Device-specific code
- `third_party` - External dependencies

## Build System Integration

### GN Build Integration

Most tools depend on GN build output:

1. **Enable dependency tracking**:
   ```bash
   ./build.sh --product-name {product} --gn-args check_deps=true --build-only-gn
   ```

2. **Output location**: `out/{product}/deps_files/`

3. **File format** (JSON per module):
   ```json
   {
     "deps": ["//path/to:module"],
     "external_deps": ["part:module"],
     "module_label": "//path:to(//toolchain)",
     "part_name": "part_name"
   }
   ```

### CI/CD Integration

1. **Pre-merge checks**: Use `csct_online_entry.py` to validate PRs
2. **Dependency tracking**: Use `check_deps.py` in nightly builds
3. **Documentation**: All tools support `--help` for usage information
